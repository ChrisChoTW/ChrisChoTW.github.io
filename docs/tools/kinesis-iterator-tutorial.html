🏢 實際案例分析

🛒 電商平台 - 訂單處理系統

需求：用戶下單後，需要庫存扣減、支付處理、發貨通知

選擇：傳統 MQ

原因：

  • 每個訂單只需處理一次，避免重複扣款
  • 需要低延遲，用戶期望即時反饋
  • 任務性質明確，不需要歷史回放
  • 失敗後可以重新入隊處理
📱 社交平台 - 用戶行為分析

需求：追蹤用戶點擊、瀏覽、分享行為供推薦引擎和商業分析使用

選擇：Kinesis Stream

原因：

  • 同一個用戶行為需要被多個系統使用
  • 需要保存歷史數據供離線分析
  • 可以重新處理歷史數據來改善推薦算法
  • 支持實時和批處理雙重模式

🌊 Stream 核心概念

🌊 大水缸概念

Kinesis Stream 就像一個巨大的「數據水缸」

💧 每一筆資料都是一滴「水」，不斷流入水缸

📍 Iterator 是你的「讀取指針」，決定從哪裡開始讀

⏰ 水會保留一段時間（24小時-365天），然後自動流掉

💧Stream（資料流）

就像不斷流動的河流
資料持續流入，按時間順序排列，每筆資料都有獨特的序號和時間戳。 可以同時有多個「觀察者」在不同位置讀取。

📍Iterator（讀取指針）

就像書籤或播放器進度條
標記你目前讀到哪裡，下次可以從這個位置繼續。每個應用程式都有自己獨立的書籤， 互不干擾。

⏰時間基準點

就像銀行的營業時間
當你建立 Iterator 時，「現在」這個時間是由 Kinesis 服務端決定， 不是你本機的時間。就像銀行開戶時間以銀行時鐘為準。

🤔 Iterator 類型對比

📖TRIM_HORIZON：完整回憶

從出生開始翻閱人生相簿
像是回顧你的完整人生，從小時候學走路、第一天上學，到工作的每一天。 每一個還「記得」的重要時刻都會被重新體驗。

🌅LATEST：活在當下

只關注接下來會發生的事
就像從現在這一刻開始記錄生活，過去的事來不及參與， 只有從你開始「觀察」之後的新事件才會被注意到。

🎯AT_SEQUENCE_NUMBER：指定起點

從特定時刻開始回憶
像是在人生相簿中直接翻到某一頁（比如高中畢業）， 然後從那個特定時刻開始往後看。

📖TRIM_HORIZON

從第1集開始追

完整體驗整個故事，不錯過任何劇情細節，適合想要完整了解背景的觀眾。

🌅LATEST

只看新播出的集數

忽略過去劇情，專注於最新發展，適合只關心現在狀況的觀眾。

🎯AT_SEQUENCE

從指定集數開始

精確從某集開始看，適合知道特定起點的觀眾。

🕐 Iterator 工作流程

步驟 1
呼叫 getShardIterator()

Client 請求建立 Iterator，指定類型（TRIM_HORIZON 或 LATEST）

步驟 2
Kinesis 記錄時間點

服務端記錄當前時間作為基準點，生成唯一的 Iterator Token

步驟 3
使用 Iterator 讀取

Client 使用 Token 讀取資料，根據類型返回相應記錄

步驟 4
Iterator 更新或失效

讀取後 Iterator 位置更新，5 分鐘不用則自動失效

🎯 Iterator 機制詳解

🔍 Iterator 是什麼？

Iterator 是讀取 Kinesis Stream 資料的「書籤」，它記錄你當前讀到哪裡，下次從哪裡繼續讀。

🔄

TRIM_HORIZON

從最古老資料開始讀
適用：日誌分析、數據移轉、全量處理

⚡

LATEST

從最新資料開始讀
適用：即時監控、即時告警、即時分析

⏰

AT_TIMESTAMP

從指定時間開始讀
適用：故障從放、特定時間分析

🔢

AT_SEQUENCE_NUMBER

從指定序列號開始讀
適用：精確重播、錯誤復原

• 錯誤恢復
• Checkpoint 機制
• 精確重播

🎆 總結與決策指南

🎯 Kinesis vs 傳統 MQ 核心差異

📦 傳統 MQ

「任務分發」模型 - 訊息是要被處理的任務，處理完就可以丟棄

🎯 確保每個任務只被執行一次，避免重複處理

📝 適合：訂單處理、郵件發送、文件轉換

🌊 Kinesis Stream

「事件日誌」模型 - 記錄是發生過的事實，需要長期保存供分析

🎯 讓多個系統都能從同一份事件日誌中獲取洞察

📝 適合：用戶行為分析、交易記錄、系統監控

💡 核心差異一句話

傳統 MQ：「任務分發器」- 任務完成就丟棄 🗑️
Kinesis Stream：「事件日誌」- 事件發生就記錄 📖

📦何時選擇傳統 MQ？

✅ 適合場景：

  • 任務處理系統 - 訂單處理、郵件發送
  • 微服務通訊 - 服務間異步調用
  • 低延遲需求 - 即時通知、聊天系統
  • 簡單架構 - 中小型應用，避免過度設計
  • 成本敏感 - 低流量時較經濟

⭐ 推薦產品：

RabbitMQ, Apache ActiveMQ, AWS SQS, Azure Service Bus

🌊何時選擇 Kinesis Stream？

✅ 適合場景：

  • 大數據分析 - 用戶行為追蹤、商業智能
  • 即時儀表板 - 系統監控、業務指標
  • 事件回放 - 狀態重建、錯誤回溯
  • 多系統整合 - 同一份資料供多個下游使用
  • 合規需求 - 需要完整事件日誌記錄

⭐ 推薦產品：

AWS Kinesis, Apache Kafka, Azure Event Hubs, Google Pub/Sub

🔄 架構遷移建議

📈 從 MQ 遷移到 Kinesis 的時機

  • 資料量急劇增長 - 每日處理量超過百萬筆訊息
  • 下游系統增加 - 需要多個系統消費同一份資料
  • 分析需求出現 - 開始需要歷史資料分析和機器學習
  • 合規要求 - 法規要求保存完整操作記錄
  • 災難恢復 - 需要精確的狀態重建能力

⚠️ 遷移注意事項

  • 成本評估 - Kinesis 有最低 Shard 成本，低流量時可能較貴
  • 延遲影響 - Stream 處理延遲通常高於 MQ
  • 應用程式改造 - 需要實作 Iterator 管理和 Checkpoint 機制
  • 監控調整 - 需要監控 Shard 使用率和 Iterator Age
  • 團隊技能 - Stream 處理需要不同的思維模式和技術棧

如果答案是「不會」→ 選擇 MQ
如果答案是「會」→ 選擇 Stream
